# 모바일 키보드 & 레이아웃 최적화

- **작업일**: 2026-02-23
- **분류**: `03_UI-UX / 모바일`

---

## 문제

### 증상

모바일 웹 채팅 페이지에서 **키보드가 올라올 때 레이아웃 문제**가 발생했다.

- 키보드와 텍스트필드 사이에 **불필요한 여백** 발생
- 메인 영역과 텍스트필드 사이에 **공백** 존재
- iOS Safari 하단 주소창 모드에서 입력창이 가려짐
- 상단 앱바가 브라우저 주소창에 가려지는 경우 발생

### 원인 1 — 키보드 열림 시에도 safe-area-bottom 적용

```
[앱바]
[메시지 영역]
[입력창]
[여백] ← env(safe-area-inset-bottom) - 키보드가 올라왔는데도 적용됨
[키보드]
```

키보드가 열리면 홈 인디케이터 영역이 사라지는데, CSS에서는 여전히 `env(safe-area-inset-bottom)` 값을 적용해서 불필요한 여백이 생겼다.

### 원인 2 — 하단 브라우저 UI 미감지

iOS Safari (탭바 모드), iOS Chrome, Firefox 등은 **하단에 주소창/툴바**가 있다.

```
[앱바]
[메시지 영역]
[입력창]
[■■■■■■■■] ← 하단 주소창/툴바 (safe-area에 포함 안 됨)
```

`env(safe-area-inset-bottom)`은 하단 주소창/툴바 높이를 포함하지 않는 경우가 많아서, 입력창이 브라우저 UI에 가려졌다.

### 원인 3 — 키보드 vs 하단 브라우저 UI 구분 불가

`visualViewport.height`가 줄어들었을 때, 그게 키보드 때문인지 하단 주소창 때문인지 구분하지 못했다.

---

## 해결 방법

### 해결 1 — `--effective-sab` CSS 변수 도입

키보드 열림 상태에 따라 safe-area-bottom을 동적으로 전환한다.

```javascript
// 키보드 열림: safe-area 무시 (키보드가 홈 인디케이터를 덮으므로)
// 키보드 닫힘: safe-area 적용 (홈 인디케이터 영역 확보)
document.documentElement.style.setProperty(
  '--effective-sab',
  isKeyboardOpen ? '0px' : 'env(safe-area-inset-bottom)'
);
```

### 해결 2 — 키보드 vs 하단 브라우저 UI 구분

`visualViewport` API로 계산한 `bottomOffset` 값을 기준으로 구분한다.

```javascript
const KEYBOARD_THRESHOLD = 150; // 150px 기준

// bottomOffset >= 150px → 키보드가 열린 것
// bottomOffset < 150px  → 하단 주소창/툴바
const isKeyboardOpen = bottomOffset >= KEYBOARD_THRESHOLD;
const keyboardHeight = isKeyboardOpen ? bottomOffset : 0;
const browserBottomBar = (!isKeyboardOpen && bottomOffset > 0) ? bottomOffset : 0;
```

### 해결 3 — 브라우저별 대응

```javascript
// 브라우저 감지
const isIOS = /iPad|iPhone|iPod/.test(navigator.userAgent);
const isAndroid = /Android/.test(navigator.userAgent);
const isSamsungBrowser = /SamsungBrowser/.test(navigator.userAgent);
const isSafari = /Safari/.test(navigator.userAgent) && !/Chrome/.test(navigator.userAgent);
const isFirefox = /Firefox/.test(navigator.userAgent);

// visualViewport API 사용 (대부분의 현대 브라우저)
// Firefox Android 등 미지원 시 폴백 로직 적용
```

### 해결 4 — CSS 변수 체계

```css
:root {
  --keyboard-height: 0px;        /* 키보드 높이 */
  --effective-sab: env(safe-area-inset-bottom);  /* 동적 safe-area */
  --browser-bottom-bar: 0px;     /* 하단 브라우저 UI 높이 */
  --is-keyboard-open: 0;         /* 키보드 열림 상태 (0 또는 1) */
}
```

## 최종 결과

모바일 웹 채팅에서 키보드/레이아웃이 올바르게 동작하는 패턴이 정립되었다.

### CSS 변수 레이아웃 패턴

```
┌─────────────────────────────────┐
│ AppBar (fixed, top: 0)          │  pt: var(--sat)
├─────────────────────────────────┤
│                                 │
│ 메시지 영역                      │  pb: calc(--chat-input-height
│ (flex: 1, overflow: auto)       │       + --effective-sab
│                                 │       + --keyboard-height
│                                 │       + --browser-bottom-bar)
├─────────────────────────────────┤
│ 입력 영역 (fixed)                │  bottom: calc(--keyboard-height
│                                 │          + --effective-sab
│                                 │          + --browser-bottom-bar)
├─────────────────────────────────┤
│ 키보드 또는 하단 브라우저 UI      │
└─────────────────────────────────┘
```

### 채팅 입력 영역 코드 패턴

```tsx
// 입력 영역 (position: fixed)
<Box
  sx={{
    position: { xs: 'fixed', md: 'static' },
    left: { xs: 0, md: 'auto' },
    right: { xs: 0, md: 'auto' },
    bottom: {
      xs: 'calc(var(--keyboard-height) + var(--effective-sab) + var(--browser-bottom-bar))',
      md: 'auto'
    },
  }}
>
  <ChatInputArea />
</Box>
```

### 메시지 영역 코드 패턴

```tsx
// 메시지 영역
<Box
  sx={{
    flex: 1,
    overflow: 'auto',
    pb: {
      xs: 'calc(var(--chat-input-height, 56px) + var(--effective-sab) + var(--keyboard-height) + var(--browser-bottom-bar))',
      md: 3,
    },
  }}
>
  {/* 메시지 목록 */}
</Box>
```

## 개선 전/후 비교

| 항목 | 개선 전 | 개선 후 |
|------|---------|---------|
| 키보드 ↔ 입력창 여백 | `--sab` 항상 적용 → 키보드 열려도 여백 발생 | `--effective-sab` 동적 전환 → 키보드 열리면 0px |
| 하단 주소창/툴바 대응 | ❌ 미처리 → 입력창 가려짐 | ✅ `--browser-bottom-bar`로 높이 확보 |
| 키보드/브라우저 UI 구분 | ❌ 구분 불가 | ✅ 150px 임계값으로 구분 |
| 메시지 영역 padding | 고정값 `pb: 0` | 동적 계산 `calc(입력창 + safe-area + 키보드 + 브라우저바)` |
| 브라우저 호환성 | visualViewport 단일 의존 | visualViewport + 폴백 메커니즘 |
| iOS Safari 탭바 모드 | ❌ 미처리 | ✅ `--browser-bottom-bar`로 대응 |
| iOS Chrome/Firefox 하단 툴바 | ❌ 미처리 | ✅ `--browser-bottom-bar`로 대응 |

## 참고: 네이티브 앱 vs 웹 대응 방식

네이티브 앱 배포가 불가능한 상황에서 웹으로 모바일 대응 시, 이 방식(JS로 뷰포트/키보드 계산)이 최선이다.

| 방식 | 장점 | 단점 |
|-----|------|------|
| **네이티브 앱** | 키보드 이벤트 직접 접근, 완벽한 제어 | 앱스토어 배포/심사 필요 |
| **Capacitor/Cordova** | 웹 코드 재사용, 네이티브 API 접근 | 별도 빌드/배포 필요 |
| **순수 웹 (우리 방식)** | 배포 간편, 즉시 반영 | 브라우저별 대응 복잡, 엣지 케이스 발생 가능 |

대부분의 서비스는 모바일에서 네이티브 앱을 권장하지만, 웹만으로 네이티브급 경험을 제공해야 할 때 이 패턴을 사용한다.
